## Confirmed defects

### F1 — Medium: allowed alternatives are discarded during allocation selection

[src/tee/runtime.ts](../src/tee/runtime.ts), lines 133–137, chooses the first research-eligible market and only afterwards checks `policy.output_assets`. The ranking does not include that on-chain restriction.

Reproduction: provide a USDC market ranked above USDT, allow both research venues but allow only USDT as the output asset. The runtime throws `OUTPUT_ASSET` without obtaining a quote, even though USDT is a valid alternative. The isolated probe reproduced this behavior.

Impact: a valid owner mission fails; it does not bypass the cap or transfer to a prohibited asset. Filter/rank candidates against the on-chain output allowlist and verified adapter/token support before selecting one. Retain explicit reasons for exclusions and test both an allowed alternative and no eligible alternative.

### F2 — Medium: a normal settlement status is classified as unknown

[src/core/intents.ts](../src/core/intents.ts), line 65, omits `KNOWN_DEPOSIT_TX`. The current [official flow](https://docs.near-intents.org/integration/distribution-channels/1click-api/quickstart/making-a-request.md) lists this as a detected deposit, before settlement.

The probe supplied that status with an otherwise matching fixture quote and observed `unknown`. In [PrivateRuntime.observe](../src/tee/runtime.ts), this can prepare an unnecessary on-chain Unknown observation during normal processing.

Impact: incorrect progress/recovery behavior, not an overspend; the contract permits later Unknown → Settled/Refunded. Map this status to pending and test every documented status, an unrecognized status, malformed responses, mismatched quotes and transport failure.

### F3 — Low: the WSL wrapper can select the wrong Rust toolchain

[scripts/ubuntu.sh](../scripts/ubuntu.sh), lines 8–9, selects the compatible Node binary but does not initialize the Rust toolchain path. On this machine, `wsl.exe -d Ubuntu -- bash .../scripts/ubuntu.sh test:contract` selects Cargo 1.75.0 and fails before building because the manifest requires edition 2024.

The root `npm run test:contract` command succeeds because [scripts/contract.mjs](../scripts/contract.mjs) uses `bash -lc`, which selects Rust/Cargo 1.93.0. Initialize/check Rust consistently in the wrapper and fail with an accurate prerequisite message. Do not change the contract edition to accommodate the wrong Cargo.

### F4 — Low: unrelated WSL tasks overwrite newer check evidence with stale files

[scripts/ubuntu.sh](../scripts/ubuntu.sh), lines 40–49, copies every cached artifact and both deployment evidence files back after every command, including a failed dry-quote request. It does not limit copying to outputs generated by that command. [scripts/contract.mjs](../scripts/contract.mjs) also leaves an earlier success JSON in place when a later run fails.

Reproduction in this audit: the successful root contract test produced a new verification JSON at `2026-11-03T19:30:12Z`. After a later WSL `quote:dry` returned HTTP 401, the root contract verification file had reverted to a success dated `2026-11-02T16:28:58Z`, alongside a contract log reporting the Cargo 1.75.0 failure. This is a confirmed evidence-integrity problem, not evidence that the passing contract test failed.

Scope copies to the current command/run, record failure explicitly, and never allow an unrelated task to restore an older success report. Preserve a source revision/run identifier in each result. The contract check was repeated with its transcript and report retained directly in the ignored audit directory to avoid the wrapper overwrite.

F1–F4 were unpatched when this audit was recorded. The follow-up fixes include desired-behavior regression tests; the ignored original probes preserve the before-fix observations.

## Foundation and security assessment

The useful foundation is substantive. The vault fixes the input token, checks integer amounts and signatures before mutation, reserves usage before the asynchronous FT call, and uses a monotonic nonce. Owner policy changes preserve consumption. Only a failed FT receipt restores its original day's allowance; an oversized successful receipt and uncertain settlement stay charged. The TypeScript/Rust signing formats share a tested vector. Owner transaction recovery saves signed bytes before broadcast and reconciles hashes after interruptions.

No spending-cap bypass was established by this review. That conclusion is limited to the examined code, tests and trust assumptions; it is not a claim that the custody system is production-audited.

Several boundaries must remain explicit:

- **Allowlist membership vs actual routing:** the vault checks commitments and a pinned executor signature. The TEE is responsible for proving the hidden recipient/venue opening corresponds to the provider route. A compromised executor can lie about routing while still remaining subject to amount limits.
- **Slippage vs fair price:** the contract compares minimum output to the executor's signed quoted output. It is not an independent price oracle or a guarantee of economic fairness.
- **Privacy boundary:** the ordinary dashboard processes rehearsal data outside a TEE. The live quote provider receives amount, assets, refund account and recipient; Neslos does not attest that provider. Public-chain deposits, output minima, timing and any real lending position remain visible. The absolute original claim that all sensitive computation is inside verified TEEs is therefore not met by the current route.
- **Audit persistence vs rollback:** encryption and signatures do not establish completeness after a host restores an old valid journal. Owner-retained/on-chain checkpoints and recovery verification are required. The runtime does not yet supply the complete owner workflow for this.
- **Owner authority:** the deployed testnet account retains an owner-controlled full-access key. The guard restricts agent authority; it does not restrict a malicious or compromised owner. Production deployment must preserve that separation explicitly.
- **Budget scope:** one fixed token and UTC calendar days. Inference credits, hosting, NEAR gas/storage and future agent-service fees need their own caps if the product promises a total operating budget.

## Missing integration work

### B1 — The owner cannot operate the private path through the product

[privateCommand()](../src/core/private-client.ts) implements verified encrypted transport, but no application or script invokes it. The browser API creates an in-memory `PolicyLedger`, and its readiness data is hardcoded to rehearsal. The testnet CLI runs a fixed proof, not a general mission.

Build an owner CLI first: validate endpoint and pinned measurements, read actual vault state, send an encrypted prepare request, show the exact transaction, submit through the durable transaction journal when authorized, and follow it to settlement. Then connect the UI to that workflow with explicit mode/network/identity information. API credentials alone cannot supply these missing connections.

### B2 — Private deployment and attestation have not been demonstrated

The current Docker image launches the rehearsal server. The documented `npm run tee` expects source files and `tsx`, while the production image copies compiled output and omits development dependencies. Although the compiled TEE entrypoint exists after building, there is no dedicated deployment manifest, reviewed image identity, socket/volume setup or working provisioning record.

Package the compiled private entrypoint; pin the image; configure the real dstack socket and persistent journal; establish measurements from a trusted build/provisioning process; verify a fresh quote before sending owner secrets. Do not copy self-reported measurements from an untrusted endpoint into the allowlist and call that independent verification.

### B3 — The live path lacks integration tests and usable audit access

The committed suite does not exercise full PrivateRuntime prepare/observe, privateCommand, or live researcher orchestration. Its `validateQuote` test only reaches rejection of an invalid signature; later validation branches are not tested through a valid-signature path. Binding fixtures are explicitly not genuine Intel evidence.

The private command schema exposes only `prepare` and `observe`, with no authenticated audit export/open. Add owner-accessible receipt operations, independent identity/checkpoint verification and restart tests. Cover changed policy/nonce, failed inference, quote validation, journal-write failure, process restart, timeout/unknown results and settlement signatures.

The current private `prepare` method explicitly rejects testnet. A genuine TEE plus testnet demonstration would therefore need a separately labelled fixture-token adapter; it cannot be enabled by changing an environment variable. That route could prove private computation and on-chain spending enforcement without claiming Confidential Intents settlement or hidden public transfers.

Observation polling also has a precise contract: successful responses, including pending responses, are cached by command id. Reusing an observe id returns the original pending result indefinitely. The probe confirmed that a fresh id re-observes. Preserve request idempotency but give each new poll a new id, or redesign observation caching explicitly. Document and test this in the owner client.

### B4 — Research output currently does not control strategy selection

The private runtime obtains and verifies three reports, then independently calls deterministic `rankMarkets()` and selects the first eligible row. It never uses `reports.marketIds` or findings to choose, veto or revise the action. Keeping model output away from budget arithmetic is sound, but the current research calls mostly supply commentary.

For the intended multi-agent product, define structured evidence-backed recommendations and disagreements. Let them affect strategy selection within deterministic rules while keeping budget authority outside the model. Demonstrate at least one case where a liquidity/risk finding changes the selected action. Arbitrary free-text findings should never become privileged instructions.

### B5 — Trading, yield positions and autonomy remain incomplete

No Rhea lending deposit/withdrawal/rebalance workflow is present. The private-payment adapter fixes output to NEAR USDT, and token discovery restricts both sides to NEAR assets. There is no scheduler or unattended mission loop. External agents are neither hired nor paid for completed work.

First complete one bounded private payment/swap. A private reserve is a valid intermediate outcome if described precisely. If adding actual yield deployment, build position and withdrawal accounting and expose the public-position tradeoff; a TEE cannot make a public lending contract private.

Operational follow-up includes the 32 MB journal limit, the 1000 completed-command limit, persistent checkpoints, secret rotation, serial/single-writer deployment and recovery after a signed transaction was saved but never reached a node. The current submitOnce implementation does not rebroadcast stored signed bytes when a saved hash is unknown; distinguish that case from replacing a possibly executed payment.

## Recommended continuation order

1. **Repair and test the integration foundation:** F1/F2/F3/F4; explicit observation-id semantics; realistic successful quote fixtures; full prepare/observe/restart tests. Exit condition: the private flow is testable as a coherent service, and every injected boundary violation has a specific result.
2. **Complete the owner workflow and live audit:** endpoint/measurement configuration, on-chain state, encrypted preparation, exact transaction review, authorized submission, durable reconciliation, pause/recovery and receipt export/verification. Exit condition: one owner command sequence drives the entire flow without hand-editing code.
3. **Package and provision the genuine private runtime:** reviewed immutable image, pinned measurements, persistent storage, independently verified hardware and live NEAR AI response evidence. Exit condition: a fresh client verifies the server before disclosing its request, and substituted evidence is rejected.
4. **Prove a real confidential route:** obtain authenticated signed dry quotes, establish control of the destination Confidential Intents account, test normal/unknown/refund statuses. A bounded funded mainnet demonstration is a separate explicitly authorized step; it is not needed merely for event eligibility. If payment privacy must include the provider's computation, resolve that architecture boundary before claiming compliance.
5. **Make the existing interface show this evidence:** actual policy version/nonce/balance, verified runtime identity, a rejected attack, accepted execution, distinct settlement and an independently verifiable receipt. Complete this flow before extending to scheduling or lending management.
6. **Prepare the submission:** a reproducible public repo, accurate limitations, a short video showing the boundary hold and successful path, X post, track selection and reviewed final payload.

The strongest next milestone is one uninterrupted, verifiable flow: **owner sets policy → verified research affects proposal → guardian rejects an invalid action → an allowed action is submitted under the on-chain cap → settlement is observed → owner verifies the private receipt**. The present work gives us much of the foundation; it does not yet give us that complete result.
