## Confirmed defects and continuation

### F1 — Medium, fixed: contradictory finalized state accepted

`src/core/near.ts` requested the budget and token balance at the configuration block, but did not verify the returned block identities. Matching policy versions alone do not make balances a coherent snapshot. It also accepted remaining allowance and pause flags inconsistent with the policy.

The reader now rejects a returned block hash different from the request, differing block heights, contradictory pause state and incorrect saturating `daily_limit - used`. Lowering the daily limit below already consumed allowance remains valid with zero remaining. Four injected contradictions passed before the fix and are now rejected. This was a bad-input/proposal risk; the on-chain vault still independently enforced its own budget.

### F2 — Medium, fixed: market identity allowlists used inherited properties

The Rhea token and DeFiLlama project dictionaries were read with ordinary object lookup. Names such as `__proto__` and `constructor` were therefore treated as known entries and admitted malformed rows. The normalizer also did not reject two observations for the same supported Rhea token.

Membership now requires an own property. Duplicate supported identities reject the feed, causing the existing explicitly labelled fallback; funded private operations reject that fallback. Tests reproduced inherited-token/project acceptance before the fix and cover duplicate supported identities. The spending contract and output-asset allowlist were not bypassed by this finding.

### F3 — Medium, fixed: the current checkout did not pass verification

The initial Windows run had **255 passed, 1 failed, 4 skipped**. The failure was the new commerce signing test, which supplied an incomplete fake public key/signature to the real SDK Borsh serializer. `npm run verify` stopped before building. A separate baseline build succeeded.

The test now uses a throwaway SDK key, the SDK delegate builder/signer and the actual serializer. It checks the encoded payment, exact accepted terms, one dispatch and unresolved-nonce protection. No funded account is used. This repairs the verification defect; it does not establish a successful live paid job.

### F4 — Missing feature, completed: real owner allowlist controls

The real browser policy form could edit amounts, slippage and output assets but not venues/counterparties. It now displays membership derived from on-chain commitments and local private openings, lets the owner select members, and generates an exact version-bound `set_policy` plan.

Salts remain in local private configuration. Unknown, duplicate and empty selections are rejected. A list cannot silently drop a current member whose local opening is missing. Untouched lists are preserved, and a concurrent chain policy change invalidates the plan. Submission still uses the existing owner review and signing flow. Tests cover these boundaries and a mobile browser review without submission.

## Material unresolved issues

**B1 — Release blocker: no verified integrated private execution evidence.** Local simulations, fixture signatures, a successful image build and a public testnet transfer establish different facts. They do not establish that the complete research → guardian → vault payment → confidential settlement flow ran inside genuine TEEs. Keep strict verification enabled; do not obtain "pins" solely by trusting the server being checked.

**B2 — Architecture gap: owner commerce is outside the hard on-chain policy.** `src/owner/commerce.ts` signs direct owner-account Rhea transactions and delegated USDC payments. `CommerceBudget` enforces local lifetime reservations. It has no vault daily limit or TEE. Its public-position opt-in and exact-hash approval are useful controls, but presenting it as private autonomous Neslos spending would be false. The new [commerce documentation](COMMERCE.md) explains its separate scope and recovery rules.

**B3 — High under a hostile-host threat model: encrypted history is not a monotonic counter.** A valid older journal can be restored with the same derived enclave keys. Hashes detect alteration and retained checkpoints detect truncation when checked; they do not provide external freshness at every restart. The on-chain nonce/usage still bounds vault spending. Local inference reservations, completed-job memory and commerce lifetime totals require an external anchor or a narrower trusted-storage assumption before being advertised as hostile-host hard limits.

**B4 — Privacy claim must remain narrower than "everything is private."** Public deposits, amounts, minimum outputs, timing and public lending positions are visible. The Intents quote service sees routing fields; marketplace agents receive their briefs. Owner client plaintext and owner signing also occur on the owner's computer. Define the protected computation precisely. A TEE does not hide a public protocol's position.

**B5 — Limits bound loss, not economic correctness.** The contract checks slippage against a signed quote, not independently established fair value. Market APYs/liquidity are provider-reported and do not include an upstream observation timestamp. A compromised data source or model can produce a poor permitted decision even when spending limits hold. Models can veto candidates, but are not independent economic oracles simply because they have different role names.

**B6 — Submission readiness is incomplete.** GitHub reports the repository private. Its configured homepage, `https://neslos.vercel.app`, returned HTTP 404 at both `/` and `/api/health`. No public working demo was established. Latest base-revision CI is green, but it does not cover this working tree. No current public X demo or final submission evidence was established by this review.

The existing transitive `elliptic` advisory remains: three low-severity npm package entries, zero moderate/high/critical entries, and no automatic fix. Do not force a dependency replacement without validating the attestation path.

## Continue in this order

1. Prove an immutable TDX runtime and verified NEAR AI research with an independently approved measurement policy and a bounded, explicitly authorized infrastructure/inference budget.
2. Verify the signed confidential quote and destination ownership. Complete one allowed vault payment and its settlement/audit, alongside an attempted overspend that is rejected. Mainnet spending needs a concrete reviewed plan; testnet eligibility does not require pretending Intents has a testnet.
3. Resolve externally anchored inference/recovery accounting for the intended hostile-host threat model. Keep owner-commerce experiments outside autonomous authority until their custody/policy architecture is designed and proved.
4. Publish a runnable demo and accurate source, record the guardrail-first flow, prepare the exact submission, and have the human publish the X post and confirm the final payload.

Security is the strongest evidenced track. Privacy and DeFi need the real integration proof above. Swarms needs a visible coordination outcome; Agents needs a demonstrated commerce outcome. There is no technical basis to promise a grand prize, but a single complete, independently verifiable private flow is a stronger next investment than a wider feature list.
